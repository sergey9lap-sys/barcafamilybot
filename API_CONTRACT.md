# Полное ТЗ backend и контракт API v1 для фронтенда Barca Family

Это проект контракта для реализации на Go. Перечисленные маршруты ещё не означают, что они уже реализованы в репозитории.

## 1. Требования, которые сохраняем

### Пользовательские сценарии

Пользователь может:

- Оценивать игроков через Telegram Mini App или непосредственно в личном чате с ботом. Оба интерфейса работают с одной анкетой.
- Выставлять оценки от 1 до 5, пропускать игроков и изменять собственные оценки до закрытия голосования.
- Видеть срок завершения голосования и состояние сохранения своей анкеты.
- После отправки анкеты смотреть текущие оценки игроков и команды.
- Просматривать завершённые матчи и их окончательные результаты.
- Просматривать собственные анкеты текущего сезона.
- Смотреть рейтинги команды и игроков по сезонам, турнирам и периодам.
- Смотреть рейтинг пользователей по количеству участий в голосованиях, собственное место и накопительную статистику.

Одна отправленная анкета на матч считается **одним участием в голосовании**. Количество оценённых игроков — отдельный показатель. Повторные сохранения не увеличивают количество участий.

### Административные сценарии

Администратор может:

- Получить последний завершённый матч из Goal API либо создать матч вручную.
- Исправить соперника, счёт, дату, турнир, состав и сведения об игроках.
- Подготовить и согласовать стартовый пост.
- Открыть голосование публикацией согласованного поста.
- Закрыть голосование досрочно; по окончании установленного срока оно закрывается автоматически.
- Отдельно запросить, проверить и опубликовать итоговый пост.
- Подготовить пост со статистикой за выбранный период.
- Редактировать тексты бота, подписи кнопок, форматирование и эмодзи.
- Проверять доставку сообщений в основной канал и каналы репостов.
- Одной командой завершить текущий сезон и начать следующий.

### Зафиксированные ограничения

| Вопрос | Решение |
|---|---|
| Backend | Go + PostgreSQL |
| Футбольные данные | Goal API Free Plan |
| Администраторы | Только `ADMIN_TELEGRAM_IDS` |
| Основной канал | `CHANNEL_USERNAME` |
| Дополнительные каналы | `REPOST_TO_CHATS` |
| Активный сезон | Всегда один |
| Смена сезона | `/nextseason`, без ID сезона |
| Исходные анкеты и оценки | Только за текущий сезон |
| История | Итоговые агрегаты сезонов, турниров, игроков, матчей и пользователей |
| Размещение | Starter для тестирования → Basic для MVP → Pro при необходимости |
| Диск production | Целевой общий бюджет 5 ГБ, включая PostgreSQL и служебные файлы |
| Отдельный публичный сайт | В MVP не требуется; основной интерфейс — Telegram |

После архивирования личные оценки удаляются. **По последнему принятому правилу список собственных анкет доступен только за текущий сезон; за прошлые сезоны остаются пользовательские счётчики.** Связь «пользователь участвовал в конкретном архивном матче» отдельно не сохраняем. Общая история матчей остаётся доступной.

## 2. Общие правила HTTP API

### 2.1. Адресация и авторизация

Базовый префикс:

```text
/api/v1
```

Все пользовательские маршруты, кроме конфигурации и входа, требуют:

```http
Authorization: Bearer <session_token>
```

Вход выполняется через подписанную строку `Telegram.WebApp.initData`. Backend проверяет подпись Telegram и свежесть данных, затем выдаёт собственную сессию. `initDataUnsafe`, переданный клиентом `telegram_id`, username или chat ID не являются доказательством личности. [Проверка данных Telegram Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)

Начальные параметры:

- Максимальный возраст `initData` при входе — 5 минут.
- Допустимое опережение серверного времени — 30 секунд.
- Срок сессии — 1 час.
- Токен хранится фронтендом в памяти.
- После истечения сессии пользователь повторно открывает Mini App.
- Роль администратора проверяется сервером по env при каждом административном запросе.

Сессия — случайный непрозрачный токен; в БД хранится его хеш. Выход отзывает сессию.

Postman может выполнять запросы с действительными учётными данными пользователя. Сам по себе он не предоставляет дополнительных прав: чужой Telegram ID или ID канала не позволяют получить административную сессию.

### 2.2. Формат ответов

Успешный ответ:

```json
{
  "data": {},
  "meta": {
    "request_id": "req_opaque_id",
    "server_time": "2026-09-09T18:00:00Z"
  }
}
```

Список:

```json
{
  "data": [],
  "page": {
    "next_cursor": null,
    "has_more": false
  },
  "meta": {
    "request_id": "req_opaque_id",
    "server_time": "2026-09-09T18:00:00Z"
  }
}
```

Ошибка:

```json
{
  "error": {
    "code": "BALLOT_VERSION_CONFLICT",
    "message": "Анкета изменена в другом окне или в боте.",
    "details": {
      "current_version": 8
    }
  },
  "meta": {
    "request_id": "req_opaque_id",
    "server_time": "2026-09-09T18:00:00Z"
  }
}
```

Фронтенд принимает решения по `error.code`. `message` предназначен для показа человеку и возвращается на русском.

### 2.3. Типы и соглашения

| Тип | Правило |
|---|---|
| Идентификаторы | JSON-строки; клиент считает их непрозрачными |
| Telegram ID | Строка в JSON, `BIGINT` в PostgreSQL |
| Момент времени | RFC 3339, UTC: `2026-09-09T18:00:00Z` |
| Календарная дата | `YYYY-MM-DD` |
| Оценка пользователя | Целое число 1–5 |
| Отсутствующая оценка | `null` при удалении оценки; не превращается в ноль |
| Средние значения | JSON number либо `null`, если данных нет |
| Количества | Неотрицательные целые числа |
| Версия сущности | Целое число, увеличивается после изменения |

Публичные ID пользователей в рейтинге не совпадают с Telegram ID.

Календарные фильтры `date_from` и `date_to` включают обе указанные даты. Дата матча определяется в `Europe/Moscow`; точное время начала дополнительно хранится в UTC. Это позволяет вручную завести матч, даже если известно только число проведения.

### 2.4. Пагинация и фильтры

Для списков:

```text
limit=20
cursor=<opaque_cursor>
```

Максимальный `limit` — 100. При изменении фильтров курсор сбрасывается.

Общие фильтры статистики:

```text
season_id=current | all | <season_id>
competition_id=<competition_id>
date_from=2026-09-01
date_to=2026-09-30
```

По умолчанию `season_id=current`.

Фильтры применяются одновременно. Например, сезон + турнир + даты означают пересечение условий.

Рейтинги пользователей поддерживают сезон, все сезоны и турнир. Произвольный период внутри архивного сезона для пользовательских счётчиков не поддерживается: после удаления анкет соответствующей детализации нет.

### 2.5. Версии и повторы запросов

Изменение существующей сущности требует `expected_version`.

Мутирующие запросы, кроме входа и выхода, передают:

```http
Idempotency-Key: <UUID операции>
```

Для анкет сохраняются последняя операция и версия анкеты, без отдельного бессрочного журнала каждого автосохранения:

- Повтор последнего успешно применённого запроса возвращает подтверждённое состояние.
- Повтор старого запроса после последующих изменений получает `409`.
- Один ключ с другим содержимым последней операции получает `409 IDEMPOTENCY_CONFLICT`.
- Версия и уникальные ограничения БД исключают повторное начисление участия.

Для публикаций и смены сезона ключ связан с долговечным заданием. Повтор возвращает то же задание и не выполняет действие заново.

### 2.6. Коды ошибок

| HTTP | Основные коды |
|---|---|
| `400` | `INVALID_JSON`, `INVALID_CURSOR`, `INVALID_QUERY` |
| `401` | `TELEGRAM_AUTH_INVALID`, `TELEGRAM_AUTH_EXPIRED`, `SESSION_EXPIRED` |
| `403` | `ADMIN_REQUIRED`, `VOTE_REQUIRED`, `ACCESS_DENIED` |
| `404` | `MATCH_NOT_FOUND`, `PLAYER_NOT_FOUND`, `RESOURCE_NOT_FOUND` |
| `409` | `BALLOT_VERSION_CONFLICT`, `ENTITY_VERSION_CONFLICT`, `VOTING_CLOSED`, `LINEUP_LOCKED`, `PREVIEW_STALE`, `IDEMPOTENCY_CONFLICT`, `ROLLOVER_IN_PROGRESS`, `OPEN_POLLS_EXIST` |
| `410` | `PERSONAL_DATA_ARCHIVED`, `ENDPOINT_RETIRED` |
| `413` | `PAYLOAD_TOO_LARGE` |
| `415` | `UNSUPPORTED_MEDIA_TYPE` |
| `422` | `VALIDATION_FAILED`, `EMPTY_BALLOT`, `PLAYER_NOT_IN_LINEUP`, `INCOMPLETE_MATCH`, `EXTERNAL_ID_CONFLICT` |
| `429` | `RATE_LIMITED` |
| `503` | `TEMPORARILY_UNAVAILABLE` |

При `429` и временном `503` сервер передаёт `Retry-After`. SQL, токены, ответы провайдера с секретными данными и внутренние трассировки в ошибки не попадают.

## 3. Контракт пользовательского API

### 3.1. Конфигурация, вход и профиль

| Метод и путь | Запрос | Ответ `data` |
|---|---|---|
| `GET /config` | Без авторизации | Публичная конфигурация |
| `POST /auth/telegram` | `{ "init_data": "..." }` | Сессия и текущий пользователь |
| `DELETE /auth/session` | Без тела | `204`, сессия отозвана |
| `GET /me` | — | Текущий пользователь |

Пример конфигурации:

```json
{
  "api_version": "v1",
  "bot_username": "barcafamilyratingbot",
  "channel_username": "@channel_username",
  "timezone": "Europe/Moscow",
  "rating_scale": {
    "min": 1,
    "max": 5,
    "step": 1
  },
  "autosave_interval_ms": 10000,
  "stats_poll_interval_ms": 10000,
  "job_poll_interval_ms": 2000,
  "personal_history_policy": "current_season_only",
  "features": {
    "native_bot_voting": true,
    "user_leaderboard": true,
    "historical_match_results": true
  }
}
```

Административные IDs, строка подключения к БД и ключ Goal API здесь отсутствуют.

Ответ входа:

```json
{
  "session_token": "<opaque_token>",
  "expires_at": "2026-09-09T19:00:00Z",
  "user": {
    "id": "usr_opaque_id",
    "telegram_id": "123456789",
    "display_name": "Никита",
    "username": "example_username",
    "role": "admin"
  }
}
```

`role`: `voter | admin`. Модель отдельного владельца с назначением администраторов через БД заменяется выбранным управлением через env.

### 3.2. Сезоны, турниры, игроки и состав клуба

| Метод и путь | Параметры | Ответ |
|---|---|---|
| `GET /seasons` | Пагинация | Сезоны, новые первыми |
| `GET /seasons/current` | — | Единственный активный сезон |
| `GET /seasons/{season_id}` | — | Сведения о сезоне и доступности данных |
| `GET /competitions` | `season_id` | Турниры выбранного сезона |
| `GET /players` | `season_id`, `active`, `q`, пагинация | Игроки |
| `GET /players/{player_id}` | — | Карточка игрока |
| `GET /roster` | `season_id` | Состав клуба за сезон, включая периоды присутствия |

Сезон:

```json
{
  "id": "season_opaque_id",
  "label": "2026/27",
  "status": "active",
  "raw_ballots_available": true,
  "archived_at": null,
  "rollover_job_id": null
}
```

Игрок:

```json
{
  "id": "player_opaque_id",
  "name_original": "Pedri",
  "display_name_ru": "Педри",
  "position": "MID",
  "position_name_ru": "Полузащитник",
  "photo_url": "/media/players/pedri-v1.jpg"
}
```

Позиции: `GK | DEF | MID | FWD | UNKNOWN`.

Номер футболки и принадлежность к клубу относятся к записи состава сезона:

```json
{
  "id": "membership_opaque_id",
  "season_id": "season_opaque_id",
  "player": {},
  "shirt_number": 8,
  "joined_on": "2026-07-01",
  "left_on": null,
  "active": true
}
```

Ушедший игрок сохраняется в справочнике и исторических матчах. Скрытие из текущего состава не удаляет его статистику.

### 3.3. Матчи и список участников

| Метод и путь | Параметры | Ответ |
|---|---|---|
| `GET /matches` | Сезон, турнир, даты, `state`, пагинация | Опубликованные голосования |
| `GET /matches/current` | — | Последний открытый матч либо `null` |
| `GET /matches/{match_id}` | — | Матч и его утверждённый состав |
| `GET /matches/{match_id}/lineup` | — | Утверждённые участники матча |

Черновики доступны только через административные маршруты.

Если открыты несколько голосований, `/matches/current` выбирает последнее открытое. Единственность активного сезона не вводит дополнительного запрета на несколько открытых матчей.

Основной объект матча:

```json
{
  "id": "match_opaque_id",
  "version": 3,
  "season": {
    "id": "season_opaque_id",
    "label": "2026/27"
  },
  "competition": {
    "id": "competition_opaque_id",
    "name_ru": "Ла Лига"
  },
  "opponent_name_ru": "Валенсия",
  "venue": "away",
  "played_on": "2026-09-09",
  "kickoff_at": "2026-09-09T17:00:00Z",
  "score": {
    "barcelona": 3,
    "opponent": 1
  },
  "penalty_score": null,
  "state": "open",
  "opened_at": "2026-09-09T19:00:00Z",
  "closes_at": "2026-09-10T19:00:00Z",
  "can_vote": true,
  "raw_ballots_available": true,
  "is_demo": false,
  "counts_for_statistics": true,
  "vote_url": "https://t.me/barcafamilyratingbot?startapp=m_match_opaque_id"
}
```

`venue`: `home | away | neutral`.

Состояния голосования:

```text
draft → open → closing → closed
```

`closing` означает, что приём оценок уже завершён, а окончательный пересчёт ещё выполняется.

Участник матча содержит:

```text
player
order
participation: starter | substitute
shirt_number
entered_at_minute: number | null
left_at_minute: number | null
minutes_played: number | null
```

В список для оценивания входят стартовавшие игроки и фактически вышедшие на замену. Неиспользованная скамейка не включается. Неизвестные минуты остаются `null`.

Состав фиксируется при открытии. API не ограничивает его расчётным числом 16; начальный технический предел — 30 участников, как в прототипе.

### 3.4. Анкета, автосохранение и отправка

| Метод и путь | Назначение |
|---|---|
| `GET /matches/{match_id}/ballot` | Получить собственную анкету |
| `PATCH /matches/{match_id}/ballot` | Сохранить изменения отдельных оценок |
| `POST /matches/{match_id}/submit` | Сохранить переданные изменения и отправить анкету |
| `GET /me/ballots` | Список собственных анкет текущего сезона |

Объект анкеты:

```json
{
  "match_id": "match_opaque_id",
  "version": 7,
  "status": "draft",
  "scores": {
    "player_a": 5,
    "player_b": 4
  },
  "ratings_count": 2,
  "submitted_at": null,
  "updated_at": "2026-09-09T19:10:00Z",
  "can_edit": true
}
```

`status`: `empty | draft | submitted`.

Если анкета ещё не существует, возвращается `empty`, версия `0`, пустой `scores`.

Автосохранение:

```http
PATCH /api/v1/matches/match_opaque_id/ballot
Idempotency-Key: <UUID>
```

```json
{
  "expected_version": 7,
  "scores": {
    "player_a": 3,
    "player_b": null,
    "player_c": 5
  }
}
```

Семантика:

- `player_a` получает оценку 3.
- Оценка `player_b` удаляется.
- `player_c` получает оценку 5.
- Неуказанные игроки остаются без изменений.
- Ответ — полная актуальная анкета с новой версией.

Отправка:

```http
POST /api/v1/matches/match_opaque_id/submit
Idempotency-Key: <UUID>
```

```json
{
  "expected_version": 8,
  "scores": {
    "player_d": 4
  }
}
```

`scores` при отправке может быть пустым. Изменения и перевод анкеты в `submitted` выполняются одной транзакцией.

Обязательные правила:

1. В отправленной анкете должна оставаться хотя бы одна оценка.
2. Черновик не участвует в статистике.
3. Изменения отправленной анкеты сразу меняют учитываемые оценки.
4. Повторная отправка не увеличивает число голосовавших.
5. Удалить последнюю оценку из отправленной анкеты нельзя.
6. После закрытия голосования изменения отклоняются целиком.
7. Telegram ID берётся из сессии; в теле запроса его нет.

Для `/me/ballots` доступны `status`, `competition_id`, даты и пагинация. Элемент списка содержит краткий матч, статус анкеты, количество оценок и дату обновления. Сами оценки загружаются отдельным запросом.

Запрос индивидуальной анкеты архивного сезона возвращает:

```http
410 Gone
```

```json
{
  "error": {
    "code": "PERSONAL_DATA_ARCHIVED",
    "message": "Личные оценки этого сезона удалены после сохранения итоговой статистики.",
    "details": {
      "season_id": "archived_season_id",
      "match_results_available": true,
      "user_season_stats_available": true
    }
  }
}
```

### 3.5. Результаты конкретного матча

| Метод и путь | Назначение |
|---|---|
| `GET /matches/{match_id}/stats` | Текущие или окончательные результаты |
| `GET /matches/{match_id}/stats/timeline` | Изменение общей оценки либо оценки выбранного игрока во время голосования |

Для временного ряда:

```text
subject=team | player
player_id=<id>   # обязателен для subject=player
```

Снимки формируются раз в 5 минут при изменениях; при закрытии обязательно сохраняется итоговая точка.

Пример результатов:

```json
  "provisional": true,
  "participants_count": 12000,
  "ratings_count": 180000,
  "team_rating": 4.08,
  "rated_players_count": 16,
  "players": [
    {
      "player_id": "player_a",
      "display_name_ru": "Педри",
      "rating": 4.35,
      "ratings_count": 11500,
      "score_sum": 50025,
      "histogram": {
        "1": 200,
        "2": 300,
        "3": 1000,
        "4": 3775,
        "5": 6225
      }
    }
  ],
  "formula_version": "v1",
  "generated_at": "2026-09-09T20:00:00Z",
  "next_refresh_after_ms": 10000
}
```

Доступ:

- Во время открытого голосования — отправившему анкету пользователю и администратору.
- До отправки — `403 VOTE_REQUIRED`.
- После закрытия — любому авторизованному пользователю.
- Архивирование сезона не закрывает доступ к обезличенным результатам матча.

Текущие оценки одновременно видны в обновляемом сообщении канала — это предусмотренная часть продукта, поэтому ограничение Mini App не считается защитой от знакомства с чужими оценками.

### 3.6. Статистика команды и игроков

| Метод и путь | Параметры | Ответ |
|---|---|---|
| `GET /stats/team` | Общие фильтры статистики | Итоги команды |
| `GET /stats/players` | Общие фильтры, `sort`, пагинация | Рейтинг игроков |
| `GET /players/{player_id}/stats` | Общие фильтры | Итоги выбранного игрока |
| `GET /stats/timeline` | Общие фильтры, `subject`, `player_id`, `group_by` | Динамика по матчам или месяцам |

`sort`: `points | average_match_rating | ratings_count`, по убыванию.

`group_by`: `match | month`.

В этих интерфейсах участвуют закрытые голосования, разрешённые для сезонной статистики. Открытые результаты доступны через API конкретного матча.

Основные поля агрегата:

```text
filters                         фактически применённые фильтры
matches_count                   число матчей в выборке
rated_matches_count             число матчей с оценкой
points                          сумма итоговых матчевых оценок
average_match_rating            среднее матчевых оценок
ratings_count                   число отдельных пользовательских оценок
score_sum                       сумма исходных оценок
average_vote_rating             score_sum / ratings_count
histogram                       распределение 1–5
generated_at
formula_version
```

Для игроков добавляются `player` и количество матчей, в которых игрок участвовал. Для команды — количество анкет в выбранных матчах.

**Формулы не смешиваем:**

| Показатель | Формула |
|---|---|
| Игрок за матч | Сумма его оценок / количество его оценок |
| Команда за матч | Среднее оценок игроков, получивших хотя бы одну оценку |
| Сезонные/периодные баллы игрока | Сумма его итоговых средних за матчи |
| Сезонные/периодные баллы команды | Сумма командных оценок матчей |
| Средняя по матчам | Сумма матчевых оценок / число оценённых матчей |
| Средняя по голосам | Сумма индивидуальных оценок / их количество |

Основной сезонный показатель сохраняет поведение README — **сумму матчевых оценок**. Средние возвращаются отдельными полями.

Исторические результаты матчей позволяют поддержать фильтры по датам и после удаления исходных голосов.

### 3.7. Рейтинг пользователей и собственная статистика

| Метод и путь | Назначение |
|---|---|
| `GET /leaderboards/users` | Общий рейтинг участников |
| `GET /leaderboards/users/me` | Собственное место в том же рейтинге |
| `GET /me/stats` | Собственные сезонные и накопительные показатели |

Фильтры:

```text
season_id=current | all | <id>
competition_id=<id>
```

Пример строки рейтинга:

```json
{
  "rank": 12,
  "user": {
    "id": "usr_public_opaque_id",
    "display_name": "Никита"
  },
  "ballots_count": 48,
  "ratings_count": 720,
  "is_me": true
}
```

Правила:

- Основной рейтинг сортируется по `ballots_count`.
- Одинаковое число участий даёт одинаковое место по правилам `RANK`: например, `1, 1, 3`.
- Внутри равенства используется стабильная сортировка по публичному ID.
- `ratings_count` показывается отдельно и не меняет основной критерий.
- Черновики не учитываются.
- Отправленная анкета открытого матча уже считается участием.
- Повторные правки не создают дополнительных участий.
- Telegram IDs других пользователей не возвращаются.
- `/leaderboards/users/me` работает и тогда, когда пользователь не попадает на первую страницу.

`GET /me/stats` возвращает применённые фильтры, `ballots_count`, `ratings_count`, разбивку по сезонам и турнирам, доступность личных анкет.

## 4. Полный контракт административного API

Все маршруты этого раздела требуют `admin`. Скрытая кнопка на фронтенде не заменяет серверную проверку.

### 4.1. Матчи и ручные исправления

| Метод и путь | Тело/параметры | Ответ |

```json
{
```

- Дубликаты игроков запрещены.
- После открытия состав и параметры, определяющие статистическую выборку, фиксируются.

- Повторный импорт существующего открытого/закрытого матча возвращает ссылку на него и не создаёт дубль.

- Отсутствующие необязательные минуты или события дают предупреждение.
- Без обязательных сведений и подтверждённого состава публикация запрещена.


Стратегия идентификации:

- Сначала ищем существующую связь с ID Goal API.
- Новый внешний игрок создаётся кандидатом, если надёжного сопоставления нет.
- По одному совпадению имени автоматически игроков не объединяем.
- Администратор может связать внешний ID с существующим игроком.
- Если связь уже используется другой записью, возвращается `EXTERNAL_ID_CONFLICT`.

Для новых имён допускается автоматическое предложение транслитерации, но оно требует проверки: транслитерация не гарантирует принятого русского написания фамилии.

Фото загружаются отдельно, максимум 2 МБ, с проверкой формата и размеров. Произвольный URL для скачивания сервером не принимается.

Сверка состава выполняется первоначально, в трансферные окна и по запросу администратора. Отсутствие игрока в неполном ответе Goal API не означает автоматическое исключение из клуба.

### 4.3. Подготовка, согласование и публикация постов

Публикация представлена отдельной сущностью, поскольку у одного матча есть стартовый пост, итоговый пост и несколько доставок в каналы.

| Метод и путь | Назначение | Ответ |
|---|---|---|
| `POST /admin/matches/{id}/posts` | Создать черновик стартового или итогового поста | `201 PostDraft` |
| `POST /admin/statistics/posts` | Создать черновик статистического поста по фильтрам | `201 PostDraft` |
| `GET /admin/posts/{post_id}` | Получить черновик или состояние публикации | `PostDraft` |
| `PATCH /admin/posts/{post_id}` | Изменить редактируемые части | `PostDraft` |
| `POST /admin/posts/{post_id}/preview` | Получить финальный предпросмотр; при запросе отправить его самому администратору | `PostPreview` |
| `POST /admin/posts/{post_id}/publish` | Согласовать проверенную версию и поставить публикацию в очередь | `202 Job` |
| `GET /admin/posts/{post_id}/deliveries` | Проверить доставку в каждый канал | Список `Delivery` |
| `POST /admin/deliveries/{delivery_id}/retry` | Повторить подтверждённо неуспешную доставку | `202 Job` |
| `POST /admin/deliveries/{delivery_id}/resolve` | Разобрать неопределённый результат отправки | `Delivery` |

Создание стартового поста:

```json
{
  "kind": "opening",
  "duration_hours": 24
}
```

Создание итогового поста:

```json
{
  "kind": "summary"
}
```

Для `opening` разрешена длительность 1–168 часов; значение по умолчанию — 24. Состав должен быть подтверждён. Для `summary` матч должен быть окончательно закрыт и пересчитан.

Черновик статистического поста:

```json
{
  "report": "players",
  "filters": {
    "season_id": "current",
    "competition_id": "competition_opaque_id",
    "date_from": "2026-09-01",
    "date_to": "2026-09-30"
  }
}
```

`report`: `team | players | users`. Для `users` действуют ограничения пользовательской исторической детализации.

Основные поля `PostDraft`:

```text
id
version
kind: opening | summary | statistics
match_id: string | null
state: draft | ready | queued | publishing | published |
       partial_failure | failed | needs_review
header: RichText
footer: RichText
button
rendered_text
rendered_entities
targets
duration_hours: number | null
statistics_as_of: timestamp | null
warnings
created_at
approved_at: timestamp | null
```

У стартового поста редактируются вводный текст, завершение и подпись кнопки. Блок результатов и срок голосования формирует backend, чтобы последующие обновления не разрушали ручной текст.

Предпросмотр:

```json
{
  "expected_version": 4,
  "send_to_telegram": true
}
```

Backend отправляет такой предпросмотр только в личный чат авторизованного администратора. Передать произвольный `chat_id` нельзя.

Ответ содержит:

```text
post_id
post_version
rendered_text
rendered_entities
buttons
targets
approval_token
expires_at
warnings
```

Согласование:

```json
{
  "expected_version": 4,
  "approval_token": "<preview_token>"
}
```

Токен согласования связан с содержимым, версией матча/состава и получателями. Срок действия — 15 минут. Изменение черновика или существенных исходных данных делает предпросмотр недействительным.

**Ответ `202` означает, что команда принята. Он не означает успешную доставку в Telegram.**

При согласовании стартового поста backend одной транзакцией открывает голосование, фиксирует срок и создаёт задания отправки. Ошибка Telegram отражается отдельно в доставках; уже принятые анкеты не откатываются.

Доставка:

```json
{
  "id": "delivery_opaque_id",
  "post_id": "post_opaque_id",
  "target": {
    "username": "@channel_username",
    "is_primary": true
  },
  "state": "sent",
  "message_id": "456",
  "message_url": "https://t.me/channel_username/456",
  "attempts": 1,
  "last_error": null,
  "updated_at": "2026-09-09T19:00:02Z"
}
```

`Delivery.state`: `pending | sending | sent | failed | unknown`.

При таймауте отправки результат может быть `unknown`: Telegram мог принять сообщение. Автоматический повтор в такой ситуации не выполняется.

Ручное разрешение:

```json
{
  "resolution": "sent",
  "message_id": "456"
}
```

либо:

```json
{
  "resolution": "not_sent"
}
```

Первый вариант связывает доставку с проверенным сообщением, второй разрешает повтор. Действие записывается в аудит.

Репосты реализуются отдельными управляемыми сообщениями с одной ссылкой на голосование. Backend хранит идентификатор каждого сообщения и обновляет их независимо.

В канале используется URL-кнопка с прямой ссылкой на Mini App. Поле `web_app` обычной inline-кнопки ограничено личными чатами. [Telegram Bot API](https://core.telegram.org/bots/api#inlinekeyboardbutton)

Сохраняем существующие ключи:

```text

no_matches

btn_vote
btn_app

```

Добавляются ключи подписей рейтинга пользователей, истории голосований и шаблонов публикаций.

Формат `RichText`:

```json
{
  "text": "🔵 Оцени игроков после матча",
  "entities": [
    {
      "type": "custom_emoji",
      "offset": 0,
      "length": 2,
      "custom_emoji_id": "123456"
    }
  ]
}
```

Сохранение:

```json
{
  "expected_version": 2,
  "text": "🔵 Оцени игроков после матча",
  "entities": []
}
```

Правила:

- Смещения Telegram entities измеряются в UTF-16.
- Поддерживаются проверенные типы форматирования и безопасные ссылки.
- Для кнопок — текст и один значок custom emoji.
- Ограничения возвращаются в `GET /admin/content`: существующие короткие сообщения — до 320 символов, кнопки — до 48.
- Для постов отдельно проверяется итоговый размер сообщения Telegram.
- Веб-редактор предупреждает о снятии форматирования, если текст изменён без соответствующих entities.
- В Telegram-редакторе сохраняются исходные entities сообщения.
- Новые настройки применяются к последующим сообщениям; массовое переписывание старых сообщений не запускается.
- При отказе Telegram использовать custom emoji применяется обычный emoji, исходное оформление сохраняется.

Premium владельца сам по себе не гарантирует custom emoji в канале: у Telegram различаются условия для личных/групповых сообщений и каналов. [Правила форматирования Telegram](https://core.telegram.org/bots/api#formatting-options)

### 4.6. Единственная операция смены сезона

```http

Idempotency-Key: <UUID>
```

```json
{}
```

Ответ — `202 Job`. Команда Telegram `/nextseason` вызывает тот же сервисный метод.

**Маршрутов `/archive` и `/activate` нет. ID сезона в запросе отсутствует.**

Предусловия:

- Нет открытых или закрывающихся голосований.
- Другой переход сезона не выполняется.
- Завершаемый сезон содержит завершённые реальные голосования.

Алгоритм:

1. Зафиксировать текущий сезон в задании.
2. Заблокировать изменение данных завершаемого сезона.
3. Полностью пересчитать исходные оценки порциями по матчам.
4. Сверить количества анкет, оценок, суммы и распределения.
5. Подготовить исторические итоги команды, игроков, турниров и пользователей.
6. В одной завершающей транзакции сохранить историю, очистить исходные анкеты/оценки и открыть следующий сезон.
7. Сбросить соответствующие кеши.

Исторические результаты матчей остаются доступными. Рабочие таблицы очищаются через явно перечисленный `TRUNCATE`, без `CASCADE`, с освобождением диска и возможностью отката транзакции. [PostgreSQL TRUNCATE](https://www.postgresql.org/docs/current/sql-truncate.html)

Повтор запроса возвращает прежнее задание. Старое задание не может переключить новый сезон повторно.

Первый сезон создаётся при инициализации пустой БД из `INITIAL_SEASON`. Следующий определяется из текущего, например `2026/27 → 2027/28`.

## 5. Реализация, совместимость и приёмка

### 5.1. Схема хранения

| Группа | Содержимое |
|---|---|
| Справочники | Пользователи, игроки, сезоны, турниры, внешние идентификаторы |
| Футбольные данные | Матчи, состав сезона, фактические участники матчей |
| Рабочие данные | Анкеты и оценки текущего сезона |
| Текущие итоги | Агрегаты матчей и пользовательские счётчики |
| История | Итоги матчей, сезонов, турниров, игроков и пользователей |
| Публикации | Черновики, согласованные версии, доставки, message IDs |
| Эксплуатация | Задания, аудит, сессии, настройки текстов |

Ключ оценки:

```text
(match_id, user_id, player_id) → score
```

Ключ анкеты:

```text
(match_id, user_id)
```

Внутри БД используем компактные числовые ключи. Существующие внешние ID и ссылки можно сохранить отдельными публичными идентификаторами, не повторяя длинные строки в каждой оценке.

После сезонного пересчёта сохраняем суммы, количества, распределения 1–5, число оценённых матчей и версию формулы. Это минимальный согласованный набор; показатели, требующие индивидуальных исторических оценок, нужно определить до первого архивирования.

### 5.2. Goal API и ручной резервный сценарий

Используем `GOAL_API_KEY` и серверный адаптер к `https://api.goal-api.com/v1`.

Нужные ресурсы провайдера:

```text
GET /teams/{id}/results
GET /fixtures/{id}
GET /fixtures/{id}/lineups
GET /fixtures/{id}/substitutions
GET /teams/{id}/players
GET /players/{id}
```

Фронтенд обращается только к нашему API. Каталог состава команды у провайдера не заменяет нашу историю составов по сезонам. [Документация Goal API](https://goal-api.com/documentation)

Free Plan заявляет 1 000 запросов в день. Массовое голосование не расходует эту квоту: внешние запросы выполняются при административном импорте. [Условия бесплатного плана](https://goal-api.com/what-is-goal-api)

Планируем обычно несколько запросов на матч и до 20 с учётом дополнительных проверок/повторов. Следим за фактическими заголовками квоты; при её исчерпании используем ручное создание.

Сохраняем обработку неполных составов, отсутствующих замен, повторов игроков и несовпадений карточек. Ошибка Goal API не блокирует голосование по вручную подготовленному матчу.

Ранее рассмотренные альтернативы остаются справочными:

- API-Football Free — 100 запросов в день, доступные сезоны ограничены. [Тарифы](https://www.api-football.com/pricing)
- football-data.org Free — матчи и результаты ограниченного набора турниров; составы и замены относятся к платному набору данных. [Тарифы](https://www.football-data.org/pricing)

В MVP интегрируется один выбранный провайдер — Goal API.

### 5.3. Кеш, нагрузка и безопасность

- Mini App сохраняет изменения пакетами не чаще раза в 10 секунд, только при наличии изменений.
- Перед отправкой анкеты передаёт оставшиеся изменения в атомарный `submit`.
- Backend обновляет кеш открытых матчей раз в 10 секунд; HTTP-чтения не пересчитывают все голоса.
- Окончательные результаты формируются после закрытия.
- Рейтинги пользователей кешируются отдельно, ориентир — 60 секунд.
- Посты Telegram обновляются раз в 60 секунд при изменениях.
- Фоновые вкладки прекращают опрос; при возвращении обновляют состояние.
- На Basic Redis не требуется.

Для API предусматриваем ограничения частоты по сессии/пользователю и общий предел параллельных работ. IP используется как вспомогательный сигнал, поскольку много пользователей могут выходить через один адрес.

Сохранение и закрытие голосования сериализуются транзакциями: ответ об успешной записи выдаётся только после фиксации БД. Telegram callbacks проходят ту же проверку версии анкеты, что и Mini App.

Массовый сценарий рассчитан прежде всего на Mini App. Нативный бот остаётся функционально полноценным, но его скорость также ограничена Telegram Bot API; очередь отправки учитывает `retry_after`.

### 5.6. Порядок реализации и проверки

1. Зафиксировать этот контракт в OpenAPI с DTO, примерами, ошибками и правами.
2. Подготовить PostgreSQL-схему, миграции, Go-сервис, конфигурацию и Dockerfile.
3. Реализовать авторизацию, анкеты и общую логику для Mini App/бота.
4. Реализовать результаты, личную историю и все рейтинги.
5. Подключить импорт, ручные исправления и составы.
6. Реализовать редактор, согласование, публикации и репосты.
7. Реализовать сезонный пересчёт и `/nextseason`.
8. Переключить фронтенд и webhook, проверить восстановление и нагрузку.

Обязательные сценарии приёмки:

- Две вкладки и бот одновременно редактируют одну анкету.
- Повтор запроса после потери ответа не создаёт второе участие.
- Пропуски, удаление оценки, пустая анкета и неизвестный игрок.
- Сохранение одновременно с истечением срока голосования.
- Результаты до отправки, после отправки, после закрытия и после архивирования.
- Все фильтры статистики, равные места рейтинга, собственное место за пределами первой страницы.
- Неполный Goal API, повторный импорт и сохранение ручных русских имён.
- Устаревший предпросмотр, изменение получателей, ошибка одного репоста и неопределённая доставка.
- UTF-16 offsets, обычные и премиум-эмодзи, безопасное отображение текста.
- Поддельный Telegram ID, неверная подпись, истёкшая сессия и доступ обычного пользователя к `/admin`.
- Сбой и повтор каждого этапа смены сезона; отсутствие двойного архивирования.
- Нагрузка 2–3 тысячи активных пользователей и отдельный стресс-профиль на 10 тысяч.
- Полный набор 15,6 млн оценок, фактическое потребление памяти/диска, обновление контейнера и восстановление БД.

Критерий готовности: фронтенд может выполнить каждый перечисленный сценарий через документированный API, без прямого доступа к PostgreSQL, Goal API и токену Telegram.
